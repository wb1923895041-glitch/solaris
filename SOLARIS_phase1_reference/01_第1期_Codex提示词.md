## 2. 科学数据的硬约束

### 2.1 天体标识

对象必须明确区分**天体中心**与**行星系统质心**：太阳（10）、水星（199）、金星（299）、地球（399）、火星（499）、木星（599）、土星（699）、天王星（799）、海王星（899）。Horizons 的质心标识 1–8 不可不加说明地代替 199–899；若中心状态在所需区间受限，需标注来源、误差或合理的取舍。

使用 NASA/JPL Horizons 官方资料核对查询参数与目标 ID，不得仅根据上述清单猜测接口行为。

### 2.2 统一参考系与时间尺度

- 原始状态向量统一存储为同一参考系的太阳系质心状态（推荐 JPL Horizons：`CENTER='500@0'`，`REF_SYSTEM='ICRF'`，`REF_PLANE='FRAME'`，`EPHEM_TYPE='VECTORS'`，`OUT_UNITS='KM-S'`，`TIME_TYPE='TDB'`；实际实现须对照官方文档确认）。
- 展示时计算同一时刻的日心相对位置 `r_rel = r_body - r_sun`。如果展示日心相对速度，需 `v_rel = v_body - v_sun`。绝不把各天体分别查询的不同中心向量直接拼接。
- 用户 UI 输入与展示使用带时区标记的日期/UTC；计算层明确转换到 TDB，记录闰秒版本/转换库；严格避免 `Date.now()` 与 JPL 历元混为一谈。不要未经验证地假设 UTC 等于 TDB。
- 保存原始单位为 km、km/s、TDB 时间信息，渲染层单独做显示单位转换。CPU 中位置与速度保留双精度。
- 数据文件每个对象标注 ID、数据来源 URL、查询参数、采样时间、有效时间区间、版本、时间尺度、参考系和中心。

### 2.3 星历生成与范围

- 优先用独立数据构建脚本（Python/Node）离线获取并生成本地缓存，浏览器播放不得每帧调用 Horizons 远程接口。
- 默认演示范围先建议 2020-01-01 至 2035-01-01 UTC；须结合实际数据体积和历表支持确定，可缩小但必须明确写在 UI 和报告中。不得宣称已覆盖数百年而未验证。
- 提供 `{positionKm, velocityKmPerSec, timeTdb, source}` 数据接口；可使用位置速度联合的分段 Hermite 插值，但需对**未参与插值拟合的抽检时间点**与 Horizons 做对照。
- 外推、无数据区间、历表异常、网络/构建失败必须明确提示，不能偷偷使用假圆轨道填补。
- 对多天体采样策略进行体积评估；不要为内行星与外行星统一盲目生成极细采样。

### 2.4 轨道线的含义

- “历史/未来轨迹”可由同一时标下的历表位置采样得到，并明确覆盖范围。
- “整圈近似轨道线”如果来自某一历元的瞬时轨道根数，只能标识为**近似轨道几何**，不是未来所有日期的高精度运行路径。
- 在演示数据时间窗内，无法画出海王星完整 165 年公转轨迹时，不得用不明来源的圆环冒充完整精确历表。
- 轨道平面、轨道倾角与空间三维关系应真实计算；不能强制把八大行星放到一条二维水平直线上。

## 3. 场景工程实现

### 3.1 空间层

- `CelestialBodyCatalog`：唯一可信的天体目录（ID、名称、物理参数及来源）。
- `EphemerisProvider`：给定时间获取全部天体物理状态，统一异常处理。
- `TimeController`：暂停、播放、倍率、跳日期、重置到演示起点，所有画面订阅同一模拟时间。
- `CoordinateTransform`：SSB/日心变换、km/AU、场景缩放和轴向适配。
- `SolarSystemScene`：太阳、八大行星、轨道、标签、灯光、星空、相机。
- `OrbitPathRenderer`：有明确时间/轨道类型的路径生成与缓存。
- `CameraDirector`：自由观察、聚焦、返回总览，有平滑状态转移和冲突规避。
- `ScaleMode`：科学比例、探索比例两种可切换表示；本期局部模式先保留接口。

Three.js 不承担物理积分和时标转换。科学数据计算尽量与渲染引擎解耦。

### 3.2 物理位置与渲染位置分离

- 严格模式：行星半径和轨道半径使用**一致的物理长度映射**。
- 探索模式：允许非线性显示距离与放大行星，但清楚标注“探索比例：尺寸/距离经过可视化调整”，且其真实天体状态向量**不改变**。
- 探索模式的非线性空间映射可能使可视化轨迹不再满足几何意义上的开普勒椭圆：物理计算、距离/速度读数、轨道参数始终使用真实状态；UI 必须标注。
- 采用浮动原点/camera-relative 变换和局部对象层次，避免大尺度坐标在 GPU 的 Float32 中抖动。
- 不得为了让行星在屏幕中并排好看而更改同一模拟日期的真实位置。

### 3.3 初步外观（只做到基础但不低劣）

- 太阳有合理的自发光表现，太阳光源照亮行星正确的朝日半球。允许临时高质量程序纹理或许可明确的科学影像。
- 八颗行星要有**准确身份的表面特征**，避免纯色球。地球海洋/大陆/云层可做适度简化；木星与海王星不能用岩石表面质感。更高质量贴图和行星环留给第 2 期。
- 球体采用适合镜头距离的几何分段、mipmap、各向异性过滤；保证无明显贴图接缝，正常昼夜边界。
- 黑暗环境优先，远景背景不能覆盖或误导天体位置；星星背景作为视线参考，禁止当作有科学距离的恒星目录。
- 轨道线是极细的冷灰蓝色，当前选中轨道可以轻微提亮；禁止所有轨道高强度霓虹。
- 标签只在可阅读时显示；需要屏幕空间避让和选中优先级，不能大量重叠。

## 4. 基准图约束与布局

总体审美：高水平科学天文馆，沉浸式 3D，黑色深空，克制的科学仪器 UI。

2560×1440 主视图包含：
1. 顶部：SOLARIS、当前空间视图、数据来源/比例状态。
2. 左侧：太阳+八大行星目录（可搜索可聚焦）。
3. 中央：可自由旋转/缩放的实时 3D 太阳系；太阳应产生强烈但不刺眼的视觉主次，轨道视线清晰。
4. 右侧：选中天体的中文名/英文名、简介、真实半径/距离/速度/轨道数据及来源按钮（暂无数据时显示“尚无核验数据”，不捏造）。
5. 底部：完整模拟时间、播放/暂停/速度档位、日期跳转、科学比例/探索比例状态。

这里的“构图参考”是信息层级与质感，不是将概念图截图当 Three.js 背景，也不是把八大行星固定在一条线上。若真实日期的位置让部分行星遮挡，应通过相机、标签避让、聚焦和适度 UI 布局处理，而不是伪造坐标。

交互：左键选中；鼠标拖动旋转、滚轮缩放、双击聚焦；`Space` 暂停/继续、`F` 聚焦、`Esc` 返回总览。UI 控件与画布拖拽事件不得冲突。所有操作仅要求桌面浏览器，不做移动适配。

## 5. 科学验收（强制自动化）

A. **天体身份**：太阳与八大行星共 9 个主要场景对象；目录、名称、ID、数据来源准确。

B. **状态向量**：至少三个分散日期（例如 2024-01-01、2026-10-29、2030-01-01，均转换到统一时标）对八大行星与太阳的状态进行比对。原始数据文件生成点不能作为全部独立验证点；须包含未参与拟合的抽样时间。每个天体报告位置误差 km、AU，速度误差 km/s，并说明误差的坐标系与参考点。

C. **时间机制**：暂停状态不随帧数漂移；同一 UTC 跳转重复位置一致；倍率切换不改变指定时间的结果；刷新能恢复明确的默认状态。

D. **比例**：科学比例模式中，任意两个天体半径和间距的显示比例符合统一映射；探索模式有醒目标识，模式切换只改变渲染位置与尺寸，不篡改物理状态。

E. **轨道**：行星轨道不是虚构同心圆；在实际状态时间窗内显示轨道倾角与偏心率，标签不超出实际数据的精度声明。

F. **数值边界**：采样区间外明确报错/限制；查询失败或异常样本不能静默退化成假数据。测试样例覆盖闰年、UTC/TDB 转换、零倍速、时间窗边界和坐标来源不一致。

G. **真实浏览器**：Chrome/Edge 中运行，1920×1080 和 2560×1440 截图；录制至少 30 秒连续播放、日期跳转、地球聚焦与返回总览的操作；报告实际平均 FPS 与帧时间和测试设备，不编造。

H. **视觉达标**：与参考图并排评测太阳主视觉、各天体可识别度、层次光照、相机景深感、文字清晰度、信息面板布局。提供 3 张同尺寸真实运行截图，而不是再生成几张概念图冒充实现。
